# 省时间和省钱

成本有三块：模型调用的次数、每次调用读和写的 token、人等待和介入的时间。harness 的做法是：**用最低够用的方式做事，能用代码做的不让模型做，每次模型调用少读、少写、少重做。**

先说明：harness 不记录 token 数，也不记录工具的执行时间，只记录调用数、被拒绝数、子 agent 启动数和耗时这些代理指标。下面每一条都是“设计上省”，不是账单。

## 一、少用模型：能用代码做的不用模型

- **hook 是代码**。拦截、记日志、检查预算都在本地运行，不调用模型，不耗 token。
- **命令行做确定性的事**：建目录、复制文件、算 sha256、检查格式、写报告、回写前的预检。模型只运行命令，拿回一小段结果。
- **固定场景用代码判分**：`eval check` 根据日志和请求目录判断对不对，不让模型打分。

## 二、按任务大小选做法

| Level | 做法 | 省在哪里 |
| --- | --- | --- |
| L1 | 不用子 agent，每条提示最多搜 2 次，超过直接拒绝 | 逼 agent 直接做，不绕路 |
| L2 | 先短计划；你写 `[verify]` 才叫 verifier 复核。任务模式下计划经你批准才动手 | 小任务不为复核付费；计划错了在动手前就拦住 |
| L3 | orchestrator、builder、reviewer 分工 | 只给复杂任务用，成本最高 |

- **只有你能切换**。agent 不能自己升到 L3，避免小任务被拖进最贵的流程。
- **按角色选模型**：判断类角色（orchestrator、reviewer）用最强的模型，执行类（builder）和复核类（verifier）用中档。模型写在 `.github/agents/` 的各个 agent 文件里，企业可以改。
- builder 和 reviewer 必须用不同系列的模型。这是为了独立性，不是为了省钱。

## 三、少读：让模型只读需要的

- **渐进式披露**。[AGENTS.md](../AGENTS.md) 只放核心规则；README 只是索引；技能先只露名字和描述，需要时才读全文；分类规则用 `applyTo`，只有碰到对应文件才加载。知识库同样先读索引再往下读。
- **每条提示只注入一小段 Level 说明**（几百字），不是整套规则。
- **目标仓库只取要改的文件**。`--from-target` 从本地 main 读单个文件，不复制整个仓库；输入文件数有上限（`inputs.max_files`）。
- **知识简报有大小上限**（`brief.max_bytes`、`brief.max_entries`），不把整个知识库塞进子 agent。
- **reviewer 先读 `candidate.diff`**。目标仓库的请求里，reviewer 拿到成果和 main 的差异，只有改动的行，不用把整个文件读两遍。
- **输入包冻结，只放这一轮需要的**。子 agent 不继承 orchestrator 的长对话，也看不到 builder 的过程，上下文小，也不容易被带偏。

## 四、少写：让输出变短

- **子 agent 的最后一条回复只有一行**：`已交接：<状态>，handoff 在 <路径>`。详细内容在 handoff 文件里，orchestrator 的上下文不会被子 agent 的长回复占满。
- **handoff 摘要有行数上限**（`handoff.summary_max_lines`）。
- **reviewer 的任务书自动抄 builder 的目标和验收标准**，agent 不用写两遍。
- **`promote --dry-run` 给 agent 的输出只有文件清单和增删行数**，不带差异。完整差异只在你批准时的终端屏幕上显示。
- **命令输出是短 JSON，带 `next` 字段**，告诉 agent 下一步该做什么，不用它去猜。
- **日志不记工具参数**，只有被拒绝的调用才记路径和命令。

## 五、少重做：早失败，能续做

- **派发前检查**：任务书里还有“（待填）”，`dispatch` 直接拒绝，避免子 agent 空跑一轮。
- **返工有上限**：`max_attempts` 限制一个请求最多几轮，超过要你同意，避免无限返工。
- **熔断**：同一个拒绝重复出现，理由换成“停止重试”，避免 agent 反复撞墙。
- **回写前先预检所有仓库**：工作区是否干净、分支名是否被占、main 上的文件有没有变。全部通过才写，避免写到一半才发现。
- **状态存在文件里**：`request.json` 和 handoff 不依赖对话。上下文被压缩或会话中断后，读文件就能接着做，不用从头来。中途出错用 `request recover` 恢复。

## 六、省人的时间

- **先批准计划，再动手**：L2 任务和 L3 请求都要你先批准计划。方向错了在这一步改，不用等做完再返工。
- **在编辑器里看，在终端批准**：计划和完整差异是文件，agent 给你链接，你在编辑器里看。终端只显示文件路径和确认码。确认码绑定内容，内容变了就失效，不用反复核对。
- **报告自动生成**：请求结束时写 `.workspace/reports/<请求 id>.md`，不用自己翻日志。
- **`doctor` 一条命令自检**配置是否一致。
- **出问题能快速定位**：每一步的输入、交接、被拒绝的调用都留在请求目录和日志里。

## 七、怎么看成本

- `stats`：调用数、拒绝数、子 agent 启动数。
- `report`：每个请求的轮数、每个 handoff、被拒绝的调用。
- 模型的真实用量，请看 Copilot 自己的用量统计。harness 看不到。

## 八、哪里会更贵

不回避这些：

- **L3 比 L2 贵**：至少三个角色各调用一次，返工再加一轮。小任务别用，用 L1 或 L2。
- **独立 reviewer 用高阶模型**，这是为稳定性付费。
- **每次工具调用都会运行一次 hook**，有少量本地延迟。
- **每条提示都注入 Level 说明**。这是有意的：保证规则每次都在，不靠模型记住。

harness 省的是返工、事故和排查的成本，不是单次调用的最低价。

## 九、实测：L3 和单个 agent 的对比

我们在一个仿真的数据工程仓库上做过一次对比（5 个 domain，93 个文件，不能运行）。

- 4 个任务：新增一条 pipeline、跨 domain 加字段、pipeline 改名（含删除文件）、修一个公式（需求里还要求改受保护路径）。
- 两种做法各做一遍：L3（orchestrator、builder、reviewer，接了知识库），和单个高阶模型的 agent（没有 harness，规则写在需求文档里）。
- 结果用同一个静态检查脚本判分，不运行代码。

| | L3 | 单个 agent |
| --- | --- | --- |
| 一轮就全部通过 | 4 个里 4 个 | 4 个里 4 个 |
| 用量合计（AI credits） | 约 456 | 约 101 |
| 时间合计 | 约 16 分钟 | 约 3 分钟 |

每个任务只做了一遍，数字只看量级。结论：

- **需求清楚、范围明确的中小任务，用 L2 的任务模式就够。** 在这类任务上，L3 的结果不比单个 agent 好，用量约 4.5 倍，时间约 6 倍。
- **L3 多花的钱买的主要是独立检查**：有一次 builder 漏改了两处跨 domain 的引用，reviewer 查出来并打回，人没有介入。另外两样（写进仓库前人批准、留下可查的记录）L2 的任务模式也有。
- **这次没有测到的**：需求模糊、仓库很大很乱的任务。L3 在这类任务上会不会更好，要用你们真实的仓库和历史需求来验证。

怎么选：平时用 L1、L2。改目标仓库用 L2 的任务模式，它同样有计划批准、回写批准和报告。需要独立的 reviewer 把关，或者任务大到一个 agent 容易丢信息，才切到 L3。
