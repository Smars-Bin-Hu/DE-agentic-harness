# 设计思想

先看全貌：有哪些组件、怎么分层。再看最关键的设计：任务分层（L1、L2、L3）。最后是其他设计，每条只写原因，规则本身以链接指向的文件为准。

## 一、全貌

### 目标

让 GitHub Copilot 在企业里做复杂任务时，**关键规则由代码强制，模型只负责判断**。它面向的场景是庞大的、有合规要求的数据工程（DE）团队的 git 代码库：没有入口、不能运行，比一般项目更复杂，必须有足够的、学习过代码之后整理的知识库才能胜任（见 [配置与定制](03-configure.md) 的“适用的代码库”）。模型会犯错、会乱试，只写说明它会忽略。所以 harness 把能确定的部分写成代码，不确定的部分写成说明，再用独立的复核补上。

### 核心可插拔组件

| 组件 | 在哪里 | 作用 | 企业怎么定制 |
| --- | --- | --- | --- |
| 规则和指令 | [AGENTS.md](../AGENTS.md)、`.github/copilot-instructions.md`、`.github/instructions/` | 所有任务都要遵守的短规则，和分类规则 | 加自己的 instructions |
| 知识库 | `knowledge-base/` 加 `knowledgebase.instructions.md` | 企业的领域资料；instructions 教 agent 按索引渐进地读 | **必须接入**，交付时为空 |
| 技能（Skills） | `.github/skills/` | 按需加载的流程和参考 | 加 `domain-` 开头的业务技能 |
| 智能体（Agents） | `.github/agents/` | orchestrator、builder、reviewer、verifier，各有分工和模型 | 改模型，加角色 |
| 工具（Tools） | Copilot 原生工具；harness 的命令行 `cli.py` | 读、写、搜、运行命令；确定性的请求操作 | 加脚本或 MCP server |
| Hooks 和引擎 | `.github/hooks/`、`.harness/engine/` | 在每次工具调用前后检查，强制规则 | 一般不改；用策略调 |
| 策略 | `.harness/policies/` | “允许什么、上限多少” | 用 `*.override.json` 覆盖 |
| 交接格式 | `.harness/contracts/` | L3 的请求、清单、交接的数据格式 | 一般不改 |
| 工作区 | `.workspace/` | L3 的执行目录、任务材料、报告 | 放任务材料 |
| 验证 | `.harness/eval/`、`.harness/tests/`、`doctor` | 固定场景、测试、配置自检 | 加场景 |

引擎里的**模块**是可插拔的：`task_level`（Level 和预算）、`gate`（拦截）、`request`（L3 请求）、`observe`（日志）、`evalcheck`（场景检查）。`task_level`、`gate`、`request` 订阅自己关心的 hook 事件；`observe` 记录每次调用；`evalcheck` 只在命令行里用。每个模块有自己的策略文件和命令。开关和订阅写在 [registry.json](../.harness/registry.json)，关掉一个模块，其他照常。

### 分层

```text
用户（切换 Level，批准关键动作）
   │
Copilot 运行时（VS Code 本地会话、Copilot SDK 会话）
   │
┌──┴─────────────────────────── 说明层：教模型怎么做 ───────────────────────────┐
│ instructions   skills   agents   knowledge-base                             │
└──────────────────────────────────────────────────────────────────────────────┘
   │ 每次工具调用前后
┌──┴─────────────────────────── 强制层：用代码拦 ───────────────────────────────┐
│ hook.py（入口）→ adapters（识别运行环境）→ core（状态、合并结果）              │
│                  → 模块：task_level  gate  request  observe  evalcheck        │
└──────────────────────────────────────────────────────────────────────────────┘
   │ 读                              │ 读和写
┌──┴────────────── 数据 ──────────┐ ┌┴──────────── 工作区和目标仓库 ─────────────┐
│ policies（规则的数字）           │ │ .workspace（L3 唯一的写入区）                │
│ contracts（交接格式）            │ │ 目标仓库（只读 main；promote 经人批准才写）   │
└──────────────────────────────────┘ └──────────────────────────────────────────────┘
```

- **说明层**：模型会读，也会忽略。
- **强制层**：模型忽略不了。一次工具调用的路径是：模型发出调用 → Copilot 运行 hook → `hook.py` 识别运行环境，把事件交给订阅的模块 → 每个模块给出放行、询问或拒绝 → 合并（拒绝优先）→ 结果返回给 Copilot。
- **数据**：规则的数字放在策略里，代码和文档里不写死。策略经常调，交接格式很少改，所以分开放。

## 二、关键设计：任务分层（Task Level）

### 为什么要分层

任务有大有小。小任务走重流程，浪费时间和费用；大任务走轻流程，容易出错、没人复核。所以 harness 把工作方式分成三级，由你按任务选。**Level 只控制 agent 的工作方式和探索量，不改变任何权限**：gate 对三个 Level 一样有效。

### 三个 Level

| | L1 | L2 | L3 |
| --- | --- | --- | --- |
| 名称 | 确定任务 | 标准工程任务 | 复杂、编排任务 |
| 适合 | 改动小、做法清楚：改一行配置、解释一段代码、查一个字段 | 相关的几个文件、有边界的改动：加一个字段并改相关脚本 | 跨系统或多个仓库、复杂的根因分析、结果要回写仓库、需要独立验证 |
| agent 怎么做 | 不写计划，直接做 | 先写短计划再做 | 必须有计划；任务拆给专门的角色 |
| 子 agent | 不用 | 只在你开启复核时用 verifier | orchestrator 调度 builder 和 reviewer |
| 验收 | agent 自查 | 默认自查；写 `[verify]` 开启独立复核 | reviewer 独立验证 |
| 成本 | 最低 | 中等 | 最高：多次模型调用、多轮 |
| 怎么进入 | 默认 | 提示开头写 `/l2` 或 `[L2]` | 在 Copilot Chat 里选 `orchestrator` agent |

怎么选：**用最低够用的 Level**。拿不准就从 L1 开始，agent 发现任务太大会停下来告诉你原因，建议你换。

### L3 是什么（第一次用请先读这一节）

L3 不是“更强的模式”，而是**一个有分工、有交接、有人批准的流程**。它解决的问题是：一个 agent 自己做、自己检查，容易漏、也容易自圆其说。L3 把这件事拆开：

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| **orchestrator**（编排员） | 理解任务，写计划，准备输入，派发给 builder 和 reviewer，判断返工还是验收，向你汇报 | 不自己写成果，不改 reviewer 的结论 |
| **builder**（执行者） | 按任务书做出成果，自测，写交接 | 不评审自己 |
| **reviewer**（评审员） | 只拿到成果，按验收标准独立验证，给出通过、失败或阻塞 | 不修改成果 |

builder 和 reviewer 必须用不同系列的模型（[agents.json](../.harness/policies/agents.json)），避免同一种思路犯同一种错。

**一个请求的过程**：

```text
你：选 orchestrator，说任务、任务目录、分支名
   │
orchestrator 建请求 ─ 取文件（目标仓库的 main）─ 写计划
   │
你在编辑器里看计划 → 在终端批准（没批准不能开第一轮）
   │
┌─ 一轮 ───────────────────────────────────────────────┐
│ 派发 builder → builder 做成果并交接                    │
│ 派发 reviewer → reviewer 独立验证并交接                │
│ 通过 → 往下；失败 → 返工，再来一轮（有轮数上限）        │
└──────────────────────────────────────────────────────┘
   │
promote 计划（dry-run）→ 你在编辑器里看差异，在终端批准 → 写入目标仓库的新分支，不提交
   │
结论（accepted、hitl、abandoned）→ 自动写报告 → 会话回到 L1
```

要点：

- **所有执行都在请求目录里**（`.workspace/sandbox/requests/<id>/`）。输入包、交接、报告都留在那里，出错能回头看。
- **仓库只有 promote 一条路径会改**，而且必须你在自己的终端批准。提交、推送、建 PR 永远由你做。
- **需要你决定时，流程会停下来**（等批准、返工超过上限、要改需求），不会自己往下闯。这叫 HITL（人在回路）。
- **什么时候用 L3**：跨仓库的改动，要回写仓库，需要独立验证，或者任务大到一个 agent 容易丢信息。
- **什么时候别用**：需求清楚的中小任务。L3 要多次调用模型，慢、贵，这类任务用 L2 的任务模式。

**L2 的任务模式**是日常开发的主力：一个 agent 做，人把两道关。

```text
你：/l2，说任务目录、目标仓库、知识库
   │
agent：task start ─ 读需求和知识库 ─ 写 PLAN.md，停下
   │
你在编辑器里看计划 → 在终端批准（没批准不能写 DEV/）
   │
agent：task fetch 取文件到 DEV/ ─ 在 DEV/ 里改 ─（你写了 [verify]）verifier 读差异复核
   │
task promote --dry-run → 你在编辑器里看差异，在终端批准 → 写入目标仓库的新分支，不提交
   │
task close → 自动写报告
```

它和 L3 用同一套批准和回写的代码，少的是请求目录、交接文件和独立的 reviewer。为什么两个批准都放在终端：对话里的确认框可以被“本会话都允许”关掉，终端里的确认码不能。为什么内容在编辑器里看：计划和差异在终端里不好读，所以终端只显示文件路径和确认码。

完整的步骤和每条命令见技能 [harness-orchestration](../.github/skills/harness-orchestration/SKILL.md)，功能说明见 [02-features.md](02-features.md)。

### 谁来切换

只有你。hook 读你的提示原文里的标记；agent 运行 `level set` 会被拒绝，它只能建议你切换。原因：agent 自己升级 Level 会放大成本和风险，这个决定要由你来做。L3 请求进行中，`/l1`、`/l2` 标记会被忽略。

### 预算

每个 Level 对每条提示有搜索次数和工具调用的上限。L1 的搜索超限直接拒绝（逼 agent 少搜、直接做），其余超限只记录。数字在 [task-levels.json](../.harness/policies/task-levels.json)。

## 三、其他关键设计

### 用代码拦，用说明教

- 能确定的部分，用 hook 和命令行强制：危险命令、越界写、没 `dispatch` 就调子 agent。
- 不能确定的部分（需求对不对、成果好不好），写成说明和技能让模型做，再用 reviewer 独立复核。
- harness 不替模型思考，输出质量仍取决于模型。它把错误挡在边界上，把事实留在日志里。

### 一条规则只有一个主要来源

[AGENTS.md](../AGENTS.md) 放所有任务都要遵守的短规则。细则放在 `.github/instructions/`、`.github/skills/`、`.harness/policies/`。其他地方只放链接和一句话，不复制全文，避免改了一处忘了另一处。

### 渐进式披露

不要一次加载全部内容。README 是索引，AGENTS.md 只放核心规则，技能先只读名字和描述，需要时才读全文。知识库同样：先读索引，再按需往下读。这样上下文短，agent 不容易被无关内容带偏。

### hook 自己出错时放行

hook 只在明确违反策略时拒绝。它自己出错（配置写坏、解析失败）时放行，并写入 `hook-errors.jsonl`。hook 在每次工具调用前运行，误伤的代价比漏拦大。`doctor` 负责发现配置问题。

### 人批准关键动作，批准不能被 agent 代劳

回写仓库（promote）、恢复仓库、批准 git 写命令，都要你在自己的终端里打字确认：

- 要真终端（管道、脚本不行），agent 运行它们会被 gate 拒绝。
- 弹窗确认不够用：VS Code 的“Allow in this Session”会关掉它，所以关键批准不用弹窗。
- 确认码来自计划或命令本身，计划在批准后变了就失效。

### admin：权限跟着会话，不跟着 agent

二开 harness 要改 guardrail 文件。hook 的输入里没有主 agent 的名字，所以“选了 admin agent”不能当成放行的依据：别的 agent 也会被当成 admin。
放行的依据是会话状态里的 admin 开关，只有你在终端输入确认码才能打开，状态文件在 admin 模式下仍然不能写。
admin agent 文件只负责教它怎么做；admin 模式站在三个 Level 之外，不和任务、请求混用。

### 请求目录是 L3 唯一的写入区

所有目录、复制、计数、上限由命令行做，文件由命令行校验。这样出错时能看到每一步留下了什么，仓库只有 promote 一条路径会改，返工每一轮的输入都冻结，可以事后对照。

### 目标仓库：只取要改的文件，不动工作区

企业的仓库文件很多，不可能整个复制。目标场景是数据工程 pipeline 代码库：没有入口、不能在本机运行，按 domain 或功能存放大量类型混杂的文件（Python、SQL、`.json`、`.sh`、PowerShell）。所以 reviewer 靠读和差异来评审，不靠运行测试；评审和计划的质量取决于知识库，知识库是这类仓库的必需品，不是附加项。harness 用 `git` 读本地 main，把计划里要改的文件取进沙箱；回写时在新分支上写文件，不提交。你的工作区、当前分支、已有的提交都不被改动，出问题可以用 `request recover` 或 `git` 命令恢复。

### 长任务：用文件记住，不靠对话

对话会被压缩，session 会换，几天后 agent 什么都不记得。所以长任务把三样东西存成文件：中心思想（`GOAL.md`）、步骤清单（`TODO.md`）、进度指针（`NOW.md`）。这也是开发这个仓库用的办法：先有中心思想，再拆步骤，一步一步做、自验、让人验收。

- **只用文件，不加命令和状态机**：agent 直接读写，人也能直接改。记录和磁盘不一致时以磁盘为准。
- **人把关**：只有用户启动，只有用户说“通过”步骤才通过。成本是 agent 自己宣布通过时没有代码拦它，靠说明约束。
- **不改 gate**：L2 任务模式和 L3 进行中不能写这些文件，流程里规定“开工前写指针，结束后更新”，不为它开例外。

### 不做的事

- 不做沙盒：终端命令可以写任何路径，gate 只拦常见写法。需要强隔离用操作系统或容器。
- 不自动 push、建 PR、fetch、pull。这些对外的动作永远由人做。
- 不自动回滚跨仓库的写入：中途出错就停下来，说清楚做了什么，由人恢复。
- 不把业务知识放进仓库。`knowledge-base/` 交付时是空的，由企业接入。
