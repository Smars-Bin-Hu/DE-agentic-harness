# 设计思想

为什么这样做。每一条只写原因，规则本身以链接指向的文件为准。

## 用代码拦，用说明教

模型会犯错、会乱试。只写说明，它会忽略。所以：

- 能确定的部分，用 hook 和 CLI 强制。例如危险命令、越界写、没 `dispatch` 就调子 agent。
- 不能确定的部分（判断需求对不对、成果好不好），写成说明和技能，让模型去做，再用 reviewer 独立复核。
- harness 不替模型思考。输出质量仍取决于模型。它做的是把错误挡在边界上，把事实留在日志里。

## 分层

- **规则**：[AGENTS.md](../AGENTS.md) 放所有任务都要遵守的短规则。细则放在 `.github/instructions/`、`.github/skills/`、`.harness/policies/`。一条规则只有一个主要来源，别处只放链接。
- **说明层**：agents、skills、instructions，教模型怎么做。
- **强制层**：`.harness/engine/` 的 hook 和 CLI。模块（`task_level`、`gate`、`request`、`observe`、`evalcheck`）可以单独开关，清单在 [registry.json](../.harness/registry.json)。
- **数据**：`.harness/policies/` 是“允许什么、上限多少”，经常改；`.harness/contracts/` 是“交接数据长什么样”，很少改。

## 渐进式披露

不要一次加载全部内容。README 是索引，AGENTS.md 只放核心规则，技能先只读名字和描述，需要时才读全文。知识库同样：先读索引，再按需往下读。这样上下文短，agent 不容易被无关内容带偏。

## hook 自己出错时放行

hook 只在明确违反策略时拒绝。它自己出错（配置写坏、解析失败）时放行，并写入 `hook-errors.jsonl`。原因：hook 在每次工具调用前运行，它误伤的代价比漏拦大。`doctor` 负责发现配置问题。

## 人批准关键动作，批准不能被 agent 代劳

回写仓库（promote）、恢复仓库、批准 git 写命令，都要人在自己的终端里打字确认：

- 要真终端（管道、脚本不行），agent 运行它们会被 gate 拒绝。
- 弹窗确认不够用：VS Code 的“Allow in this Session”会关掉它，所以关键批准不用弹窗。
- 确认码来自计划或命令本身，计划在批准后变了就失效。

## 请求目录是 L3 唯一的写入区

L3 的 agent 只写当前请求目录。所有目录、复制、计数、上限由 CLI 做，文件由 CLI 校验。这样：

- 出错时能看到每一步留下了什么（输入包、handoff、报告）。
- 仓库本身只有 promote 一条路径会改，而且要人批准。
- 返工的每一轮输入都冻结，可以事后对照。

## 目标仓库：只取要改的文件，不动工作区

公司的仓库文件很多，不可能整个复制。harness 用 `git` 读本地 main，把计划里要改的文件取进沙箱；回写时在新分支上写文件，不提交。你的工作区、你当前的分支、已有的提交都不被改动，出问题可以用 `request recover` 或 `git` 命令恢复。

## 不做的事

- 不做沙盒：终端命令可以写任何路径，gate 只拦常见写法。需要强隔离用操作系统或容器。
- 不自动 push、建 PR、fetch、pull。这些对外的动作永远由人做。
- 不自动回滚跨仓库的写入：中途出错就停下来，说清楚做了什么，由人恢复。
- 不把业务知识放进仓库。`knowledge-base/` 交付时是空的，由企业接入。
